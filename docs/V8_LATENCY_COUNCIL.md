## Plausible sources, ordered by actionable scope

1. **Admitted metadata executor backlog / filesystem latency: strongest hostile-path candidate.** Five hostile variants fail schema validation; `/etc/passwd` is a valid string and proceeds to metadata, then returns 404 (`benchmark_ingress.mjs:110–113`; `overlay/server.py:1197–1222,647–680`). Metadata has only 1–4 workers (`server.py:393–399`), submits after extraction admission, and its queue time is absent from admission telemetry (`:828–861,865–877`). Path resolution invokes filesystem operations and even calls `is_file()` before checking `permitted` (`:667–678`). Zero admission wait therefore does **not** exclude a metadata tail; lazily created threads/cold filesystem are additional unmeasured contributors. These are candidates, not attribution of the 222 ms maximum.
   - **Shortest safe code change:** change the post-resolution condition to test `permitted` before `resolved.is_file()`; preserve 404 and canonical-path policy. This avoids a needless target stat for denied paths, not all resolution I/O. Keep it inside the already-admitted metadata stage; no pre-admission filesystem checks, separate bypass lane, or cached upload authorization. No promise this small change alone meets 200 ms.

2. **Shared event-loop/GIL work and logging amplify tails.** Schema tree scanning, error sanitization, `jsonable_encoder`, and JSON rendering are synchronous (`server.py:94–125,1742–1783`). The queue logger avoids sink I/O on the request path, but its formatter is installed on the producer-side QueueHandler (`:251–267,270–295`); JSON formatting still runs there. Completion logging runs before header send and after the app-duration sample (`request_policy.py:54–77`). Native harness does not pin log level or worker settings, inheriting deployment environment (`benchmark_ingress.mjs:26–28`). Small hostile bodies do not prove these operations independently cost 200 ms, but concurrently queued requests can wait for them.
   - **Shortest safe mitigation candidate:** explicit WARNING-level deployment logging while retaining rejection warnings, metrics and drop accounting; do not call it a pass based on a quieter harness. If formatting is moved to the listener, snapshot safe scalar trace/request context on the producer; do not pass bodies, credentials, or live ContextVars across threads. Bound error echo by total size/width as well as depth for broader hostile inputs (current byte truncation does not truncate strings). That broader-input hardening is not an explanation for these tiny six payloads.

3. **Mixed-workload evidence contention and Python CPU competition.** Missing source lookups and corrections use a four-worker evidence bulkhead (`server.py:410–420,1125–1134,1399–1407`). Publication/pruning and review share the store RLock; review takes `BEGIN IMMEDIATE` before discovering a missing extraction (`kernel/sidecar/evidence_store.py:177–224,256–284`). Store SQLite timeout is five seconds (`kernel/sidecar/storage_security.py:92–93`). Extraction workers run Python pipeline code and publish evidence (`server.py:1281–1313`), so thread bulkheads do not isolate the GIL or store lock. This plausibly contributes to the mixed 233 ms tail, **not the preceding hostile-only phase**.
   - **Shortest targeted candidate:** a tenant-scoped missing-entity lookup before opening the review write transaction; an absent immutable UUID can linearize to 404 there. If present, retain the complete existing transactional chain/TTL/field/revision validation and CAS; never accept a cached positive result. Reader-connection separation or process isolation is larger work, not an authorized quick fix. Do not increase thread counts/queue depth blindly, remove the lock, shorten SQLite timeout into new 5xx failures, or weaken publication atomicity.
